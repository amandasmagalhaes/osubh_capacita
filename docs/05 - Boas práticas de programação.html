Boas práticas de programação

Data de Publicação

31 de agosto de 2026

O que são boas práticas?

Boas práticas de programação são formas de escrever, organizar e documentar códigos para que eles sejam fáceis de entender, revisar, reutilizar e corrigir.

Um código de qualidade não é necessariamente o código mais curto ou o que executa mais rapidamente. Em análises de dados, o mais importante é que outra pessoa, ou você mesmo no futuro, consiga compreender o que foi feito e reproduzir os resultados.

Esses cuidados são úteis tanto para um pequeno exercício quanto para uma pesquisa que será atualizada durante vários anos.

Por que isso é importante?

Uma análise geralmente envolve várias decisões: quais dados foram usados, como eles foram organizados, quais filtros foram aplicados e como os resultados foram calculados. Quando essas decisões ficam registradas no código, torna-se mais fácil:

  • Entender o próprio trabalho depois de algum tempo;
  • Identificar e corrigir erros;
  • Atualizar a análise quando novos dados chegam;
  • Compartilhar o trabalho com colegas;
  • Reproduzir tabelas, gráficos e resultados;
  • Adaptar o código para outra pergunta ou conjunto de dados.

Organizar o código exige algum tempo no início, mas costuma economizar muito tempo ao longo do projeto.

Cinco princípios para começar

Um bom ponto de partida é pensar que o código deve ser:

  1. Consistente: seguir o mesmo padrão de nomes, formatação e organização.
  2. Organizado: manter arquivos e pastas em locais previsíveis.
  3. Documentado: registrar o objetivo do projeto e as decisões importantes.
  4. Claro: priorizar comandos que sejam fáceis de ler e compreender.
  5. Reutilizável: permitir que o código seja adaptado sem copiar e colar grandes blocos.

Não é necessário aplicar tudo de uma vez. O mais importante é criar o hábito de escrever o código pensando também em quem precisará lê-lo depois.

Exemplo

Os exemplos a seguir utilizam dados fictícios de uma turma.

Código 
alunos <- data.frame(
  nome = c(
    "Ana",
    "Bruno",
    "Carla",
    "Diego",
    "Elisa",
    "Felipe",
    "Gabriela",
    "Hugo",
    "Isabela",
    "João"
  ),
  idade = c(20, 22, 19, 25, 21, 23, 20, 24, 18, 22),
  nota = c(8.5, 6.0, 9.2, 7.5, NA, 5.5, 7.0, 9.5, 6.8, 8.7)
)

1. Organize as pastas do projeto

Uma estrutura simples pode ser suficiente para começar:

meu_projeto/
├── README.md
├── scripts/
├── data/
│   ├── raw/
│   └── processed/
├── results/
│   ├── tables/
│   └── figures/
└── docs/

Uma sugestão para cada pasta:

  • README.md: apresenta o projeto e explica como executá-lo;
  • scripts/: contém os scripts e documentos da análise;
  • data/raw/: guarda os dados originais, sem alterações;
  • data/processed/: guarda os dados preparados para a análise;
  • results/: guarda tabelas, gráficos e outros resultados finais;
  • docs/: guarda documentos de apoio e explicações adicionais.

Os nomes das pastas podem variar. O mais importante é que a organização seja intuitiva e seja mantida durante todo o projeto.

Atenção: dados confidenciais, senhas e chaves de acesso não devem ser enviados para o GitHub. Antes de compartilhar um projeto, confira os arquivos que estão dentro da pasta.

2. Use nomes consistentes

Nomes claros ajudam a entender o código sem precisar consultar cada linha.

Código 
# Nomes claros
idade_media <- mean(alunos$idade)
dados_processados <- alunos[!is.na(alunos$nota), ]
# Nomes pouco informativos
x <- mean(a$b)
df2 <- df[df$c > 0, ]

Algumas recomendações simples:

  • Use nomes que indiquem o conteúdo do objeto;
  • Escolha um padrão e mantenha-o em todo o projeto;
  • Prefira letras minúsculas e _ para separar palavras;
  • Evite nomes como x, objeto_final_final e teste2;
  • Evite espaços e acentos em nomes de arquivos e objetos.

Também é importante escolher um padrão para nomes de arquivos. Por exemplo:

00_importar_dados.R
01_preparar_dados.R
02_analisar_dados.R
03_criar_tabelas.R
04_criar_graficos.R

A numeração ajuda a indicar a ordem esperada de execução.

3. Divida o trabalho em etapas

Um script muito longo e sem organização é difícil de acompanhar. Podemos pensar nele como um capítulo de um livro: cada seção deve desenvolver uma ideia principal.

Código 
### Configuração ####

### Importação dos dados ####

### Organização dos dados ####

### Análise ####

### Tabelas e gráficos ####

### Exportação dos resultados ####

Em projetos maiores, cada etapa pode ficar em um arquivo separado. Por exemplo, um script pode importar os dados, outro pode prepará-los e outro pode gerar os resultados. Essa separação facilita encontrar erros e executar apenas a etapa necessária.

4. Documente o projeto

O arquivo README

O README.md é a porta de entrada do projeto. Ele deve explicar, de forma breve:

  • Qual é o objetivo da análise;
  • Quem desenvolveu o projeto;
  • Quais dados são utilizados;
  • Como as pastas estão organizadas;
  • Qual é a ordem de execução dos scripts;
  • Quais pacotes precisam ser instalados;
  • Onde encontrar os principais resultados.

Comentários no código

Comentários devem explicar o objetivo ou uma decisão importante. Não é necessário escrever um comentário para cada linha:

Código 
# Calcular a média apenas entre as observações com nota informada.
media_nota <- mean(alunos$nota, na.rm = TRUE)

Comentários que apenas repetem o código ajudam pouco:

Código 
# Calcular a média
media_nota <- mean(alunos$nota, na.rm = TRUE)

Use comentários para explicar o porquê de uma decisão quando isso não for óbvio no próprio código.

5. Priorize clareza

Prefira uma solução simples e legível a uma solução muito compacta, mas difícil de entender. Separe comandos que representam etapas diferentes e use objetos com nomes significativos.

Código 
# Separar o filtro em uma etapa que pode ser conferida.
dados_validos <- alunos[!is.na(alunos$nota), ]

media_nota <- mean(dados_validos$nota)
media_nota
[1] 7.633333

Ao criar uma tabela, gráfico ou modelo, é útil manter o objeto que originou o resultado. Assim, podemos revisar cada etapa em vez de executar uma expressão muito longa de uma só vez.

6. Evite repetir código sem necessidade

Copiar e colar o mesmo bloco várias vezes aumenta a chance de erro. Se a mesma tarefa for realizada para diferentes valores, considere usar uma função ou uma repetição.

Código 
calcular_media <- function(valores) {
  mean(valores, na.rm = TRUE)
}

calcular_media(alunos$nota)
[1] 7.633333
Código 
calcular_media(alunos$idade)
[1] 21.4

Por outro lado, não é necessário criar uma função para cada linha. A função deve esconder uma tarefa repetida sem esconder o significado da análise.

7. Evite caminhos fixos e valores desnecessariamente codificados

Um caminho como o exemplo abaixo normalmente só funciona no computador de quem o escreveu:

# Evite compartilhar caminhos específicos do seu computador.
read.csv("/Users/nome/Documentos/meu-projeto/data/dados.csv")

Prefira caminhos relativos à pasta do projeto e mantenha a estrutura de pastas organizada:

caminho_dados <- file.path("data", "raw", "dados.csv")
dados <- read.csv(caminho_dados)

Também evite repetir o mesmo número ou texto em vários lugares do script. Quando um valor for uma decisão importante da análise, dê um nome a ele:

Código 
nota_minima <- 7
alunos_aprovados <- alunos[!is.na(alunos$nota) & alunos$nota >= nota_minima, ]

Isso facilita atualizar a análise e deixa a decisão mais visível.

8. Pense na reprodução da análise

Uma análise reproduzível é aquela que pode ser executada novamente e produzir resultados equivalentes, seguindo as mesmas condições.

Alguns cuidados ajudam nesse processo:

  • Não altere manualmente o arquivo de dados original;
  • Registre a origem e a data dos dados;
  • Salve os resultados intermediários importantes;
  • Registre os pacotes utilizados;
  • Mantenha a ordem de execução dos scripts clara;
  • Salve o código e as decisões junto com o projeto;
  • Use set.seed() quando houver sorteio ou simulação aleatória.

Por exemplo:

Código 
# Torna o sorteio reproduzível.
set.seed(123)
amostra <- sample(1:100, size = 5)
amostra
[1] 31 79 51 14 67

9. Revise o código em etapas

O primeiro objetivo é fazer o código funcionar. Depois, revise o resultado com calma:

  1. Confira se os dados foram importados corretamente;
  2. Examine os objetos criados em cada etapa;
  3. Verifique se os filtros e cálculos fazem sentido;
  4. Melhore os nomes e comentários;
  5. Elimine repetições e comandos desnecessários;
  6. Execute novamente o projeto do início ao fim.

Programar é um processo iterativo. Um código pode funcionar e ainda precisar ser reorganizado para ficar mais claro e fácil de manter.

10. Use o Git e o GitHub

O Git registra as versões do projeto no computador. O GitHub guarda uma cópia online e facilita o compartilhamento e a colaboração.

O fluxo básico é:

alterar arquivo → salvar → conferir alterações → commit → push

Boas práticas não são regras para complicar a programação. Elas são hábitos que tornam o trabalho mais claro, confiável e fácil de continuar.
